02 // HUNT 01

Investigating LSASS access

A process may have accessed LSASS as part of credential theft. Investigate the accessing process and supporting activity before classifying it as credential dumping.

INCONCLUSIVE25 EVENTS

Data and queries

The inventory showed 12,256 events in windowslogs with sourcetype _json, and 2,000 events in vpnlogs with sourcetype kv.

index=* earliest=0 latest=now
| stats count AS events by index sourcetype
| sort - events

The initial LSASS hunt returned 25 events:

index=windowslogs earliest=0 latest=now
EventID=10 TargetImage="*lsass.exe"
| sort 0 _time
| table _time Hostname SourceImage TargetImage GrantedAccess SourceProcessGUID TargetProcessGUID

An attempted correlation to EventID 1 using ProcessGuid returned no matches. Separate raw-event inspection confirmed process-creation events and the field existed, but did not establish that creation records for the specific accessing processes were available.

A broader GUID search returned 180 related records. That result is context, not a count of credential-dumping attempts.

Observations

  • Displayed date: 15 April 2022, approximately 08:06:02–08:06:43.
  • Source: C:\windows\system32\svchost.exe; target: C:\windows\system32\lsass.exe.
  • Hostname labels included James.browne and Micheal.Beaven; they were not treated as executing usernames.
  • Visible access masks were 0x1000 and 0x2000. These values alone do not prove memory dumping.

Finding and limitations

LSASS process access was observed, but credential dumping was not confirmed. The reviewed evidence did not establish a dump file credential dumping command or malicious accessing during the process. A familiar executable name is also insufficient to establish benign behaviour.

The later 1,271-event search had lost the GUID filter and cannot be used as LSASS-specific evidence. Its WMIC result became a separate lead for Hunt 2.

Recommended follow-up

Retrieve process ancestry and endpoint telemetry for the accessing GUIDs; examine access rights, dump-file artifacts and executable integrity. Escalate only if corroborating evidence supports credential theft.

03 // HUNT 02

Remote account creation and deletion

An account may have been created remotely through WMIC. Correlate the command with account-management records and distinguish the new local identity from similarly named accounts.

CHANGES CONFIRMEDINTENT UNKNOWN

Queries and correlation

index=windowslogs earliest=0 latest=now
EventID=1 Image="*WMIC.exe"
| sort 0 _time
| table _time Hostname User Image CommandLine ParentImage ParentCommandLine ProcessGuid

One event showed PowerShell launching WMIC under Cybertees\James, targeting WORKSTATION6 and requesting creation of Alberto through net user /add. The plaintext lab password is intentionally omitted from this write-up.

index=windowslogs earliest=0 latest=now
SourceName="Microsoft-Windows-Security-Auditing" EventID=4720
| table _time Hostname SubjectDomainName SubjectUserName TargetDomainName TargetUserName TargetSid

The creation record identified WORKSTATION6\Alberto, created by Cybertees\James, with SID S-1-5-21-1969843730-2406867588-1543852148-1000.

Recorded account activity

560784728 — group member added
560794720 — account created
560804724 — password-reset attempt
560814729 — group member removed
560824726 — account deleted

All five records displayed 08:06:02 and showed James as subject username and Micheal.Beaven as the Hostname label. TargetDomainName=WORKSTATION6 was retained separately.

The recorded group-add entry precedes the creation entry. That observed ordering is preserved rather than rewritten into an assumed lifecycle. Also a Identical displayed timestamps do not establish the account's precise lifetime, and the password reset outcome was not independently verified.

Finding and limitations

However account creation and deletion are confirmed. The matching target, account name, actor and adjacent displayed times strongly support a relationship with the WMIC command. Authorization, subsequent account use and malicious intent remain unknown. Deletion alone does not prove attacker cleanup.

Recommended follow-up

Validate whether James had an approved administrative task, check target-host authentication using the new SID and examine the PowerShell parent activity.

04 // HUNT 03

Possible exfiltration through C2 traffic

Identify permitted traffic to the lab's C2-labelled destination, calculate recorded volume and distinguish suspicious communication from proven sensitive-data exfiltration.

SUSPICIOUS TRAFFIC126,167 BYTES

Data and validation

This hunt uses the separate Day 5 dataset: index=main, sourcetype=firewall_logs. Raw samples contained src_ip, dest_ip, dest_port, action, bytes_transferred and reason.

index=main sourcetype="firewall_logs" earliest=0 latest=now
| head 3
| table _raw

Samples showed source 10.10.1.5. The room text had mentioned 10.10.1.15 the investigation used the address in the records. Blocked samples were not counted as successful transfers.

An exploratory spath aggregation produced an impossible grouped count of 2,280 despite only 1,572 source events. Its 2,018,672-byte total was rejected.

index=main sourcetype=firewall_logs earliest=0 latest=now
dest_ip="198.51.100.55" action=ALLOWED
| stats count AS events sum(bytes_transferred) AS total_bytes

Observed result

Destination198.51.100.55
Allowed events285
Recorded bytes126,167
Lab labelC2_CONTACT

The final query filters destination and action, but not source or port. Its value is therefore reported strictly as the allowed event total to that destination. Source 10.10.1.5 and port 8080 come from the earlier grouping a source and port specific total was not rerun.

An initial zero-result query searched only September 2026. Adding earliest=0 latest=now included the older dataset and returned results.

Finding and limitations

The logs contain 285 allowed events to the C2 labelled destination with 126,167 recorded bytes. This supports suspicious permitted communication and a possible exfiltration. It does not however establish transferred content, unique sessions or that all bytes represent outbound sensitive data. The C2 classification is the lab's label, not independent threat intelligence.

Recommended follow-up

Correlate traffic with web requests and endpoint processes, confirm byte-field semantics, inspect proxy or packet evidence and validate the destination classification before containment.

05 // SUPPORTING EVIDENCE

Setup and investigative pivots

Additional screenshots record dataset discovery, raw-event inspection and searches that were useful but not treated as conclusive evidence.

06 // ANALYST REFLECTION

Three valid, distinct outcomes

Hunt 1 remains inconclusive for credential dumping; Hunt 2 confirms account changes without establishing malicious intent; Hunt 3 establishes C2-labelled communication without proving sensitive-data exfiltration.

Key lessons: verify the dataset and time range; inspect actual field names; correlate identities using SIDs and processes using GUIDs; validate aggregates against source-event counts; and separate observed actions from inferred intent or impact.
